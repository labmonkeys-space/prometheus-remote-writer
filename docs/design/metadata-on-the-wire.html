DESIGN DOCUMENT · prometheus-remote-writer

Metadata on the Wire

Status: proposed, not implemented Greenfield: no compatibility with the v0.x label schema Removes: labels.attr-mode, labels.attr-include, labels.categories-mode, onms_attr_*, onms_extattr_*, onms_cat_*, _idx* Open questions: resolved 2026-09-14, see §11

OpenNMS resource metadata should travel in Prometheus as two series shapes rather than as labels on the data series. No database, no recording rules, and no rule evaluator are required at any point.

01The problem

An OpenNMS Metric carries three tag partitions: intrinsic, meta and external. Intrinsic and meta map cleanly onto Prometheus labels. External tags do not, for two independent reasons.

The key space is unbounded

Under a column encoding every attribute key becomes a distinct label name. OpenNMS generates keys that embed per-resource identity, such as latency ICMP/<ip> and JMX mbean paths. That grows the backend's global label-name index without limit, which is why labels.attr-mode defaults to off and why attr-mode=external requires an explicit allowlist (issue #112).

Label sets are immutable identities

A Prometheus series is its label set. Putting a mutable attribute on the data series means changing it forks the series, once per metric on that resource. ifAlias is the case that matters: an operator editing an interface description on the switch should not split a year of throughput history.

The allowlist addresses the first problem and not the second, and it does so by making an operator responsible for curating a list they cannot be expected to know in advance.
Principle, not a measurement. A network operator setting or improving an interface description is routine, and nothing about that action suggests it could affect monitoring. So ifAlias stays out of the data series identity on principle, whatever its churn rate turns out to be; a low rate would only make the split rarer, not acceptable. The same reasoning removes ifDescr from the data series: it is stable on Cisco, Juniper and Arista, but on Nokia SR OS and some Huawei releases it embeds the configured description, and on RouterOS and Linux it follows an interface rename. ifName is the one interface field no operator sets, so it is the only interface label that remains on the data series.

02Columns or rows: two consumers, not two options

Columns and rows look like alternatives until you notice they are serving different readers with opposite requirements. One wants a handful of attributes on every query. The other wants all of them, for one resource, and never joins anything.

03Install the plugin. That is the whole procedure.

The column view is not a convenience, it is the interface: decorating a data series from rows needs a label_replace per attribute, and two joins collide on the label name value. Nobody writes that in a panel editor. Since the column view is mandatory, it must not depend on anything optional, which rules out deriving it from a recording rule. The plugin emits it, and the promoted set is a config list.

No rules to generate, no rules to deploy, no ruler to run. Extending the column set means editing one config list on the side you already administer, not producing a rules file and loading it into the backend. One system instead of two.

Alerting works the same way

An alert expression can carry the join itself, so alerting needs no recording rules either. This matters most for VictoriaMetrics, where the usual setup has no vmalert at all.

  * on(resourceId) group_left(if_alias, if_descr) onms_resource_info
Two cautions specific to alert expressions. Scope the join to the resources the alert covers rather than joining the whole fleet every evaluation, or a minutely alert becomes the most repetitive form of the series-limit problem. And use the max by (…) form here even if you skip it on dashboards: a duplicate match during an ifAlias churn window turns a panel visibly red, but it makes an alert rule error out instead of evaluating, which is a silent loss of coverage.
The escape hatch: an operator who cannot change the plugin config, or who wants a view the plugin cannot express, can still build one with a recording rule against onms_resource_attr. Two things to know if they do. The recorded series must land in the same tenant the plugin writes under, the same X-Scope-OrgID, or every join returns empty with no error at all. And on VictoriaMetrics this is the one path that does require vmalert, since Grafana-managed alerting cannot write series back.

04What the plugin emits

# data series: only what is needed to read them, plus the stable promoted set
ifHCInOctets{resourceId="snmp/1/if1", mtype="counter", node_label="core-sw-1", if_name="Et1"}

# rows: every attribute, three label names forever
onms_resource_attr{resourceId="snmp/1/if1", key="ifAlias", value="uplink"} 1
onms_resource_attr{resourceId="snmp/1/if1", key="ifDescr", value="Ethernet1"} 1
onms_resource_category{resourceId="node/1", category="Production"} 1

# columns: the configured subset, for query ergonomics
# info.columns = if_alias=ifAlias, if_descr=ifDescr, resource_name=name   (the default)
onms_resource_info{resourceId="snmp/1/if1", if_alias="uplink", if_descr="Ethernet1"} 1
onms_resource_info{resourceId="node/1/pgDatabase/opennms", resource_name="opennms"} 1

# numerics get their own gauge, never a label value
onms_resource_ifspeed{resourceId="snmp/1/if1"} 1000000000
stays on the data seriesmtype and unit, which are not metadata about the resource but how a consumer knows whether the samples are a counter or a gauge. OpenNMS core dereferences mtype unconditionally when rendering graphs. Plus the stable promoted set: node_label, foreign_source, foreign_id, location, if_name. These need no join at all, which beats any derived view. ifDescr is no longer in this set, see §01.
rowsEverything else, ifAlias and ifDescr included. Three label names permanently, whatever OpenNMS invents, so an unknown key cannot grow the label-name index. Categories as rows also removes the need for labels.categories-mode: set membership becomes an exact match rather than a regex over a joined string or a label name per user-defined category.
columnsA short configured subset the plugin emits alongside the rows, so a fresh install has a usable query surface with no ruler. Each entry is column=key: the label name on the wire, and the OpenNMS attribute key it is read from. The default maps ifAlias, ifDescr and the collector attribute name; the last one becomes resource_name because a label called name next to __name__ is a trap in every legend and query. Changing the list forks only this series, one per resource, and leaves the data series untouched.
dropped_idx0…_idxN, resource-tree internals with no query value in any encoding; today they occupy the series identity, paying cardinality for nothing. Also every onms_attr_*, onms_extattr_* and onms_cat_* label, since rows carry that content now, and with them the labels.attr-mode, labels.attr-include and labels.categories-mode keys and the read-path branch that rebuilt tag partitions from those prefixes.

05Why the long tail must be rows

The plugin's own read path needs every attribute for a resource in order to rebuild the Metric that OpenNMS graph definitions dereference for ${name}-style placeholder substitution. Under a column-only encoding, an attribute nobody thought to allowlist is one the read path cannot restore.

06Query patterns

Dashboards

rate(ifHCInOctets[5m])
  * on(resourceId) group_left(if_alias, if_descr) onms_resource_info

Historical correctness

Point-in-time is the default behaviour of a range-vector join, so a query over old data sees the alias as it was then. To apply the current alias to historical data, pin the right-hand side with the @ modifier:

rate(ifHCInOctets[5m])
  * on(resourceId) group_left(value)
    (last_over_time(onms_resource_attr{key="ifAlias"}[1h]) @ end())

Both readings are available from the same data. Neither is available when the attribute is part of the data series identity.

Sample rate is resources divided by the re-emission cadence, and cadence is tunable against the query idiom: emit every 15 minutes and widen the query to last_over_time(…[1h]) rather than emitting every 2 minutes to stay inside the default 5-minute lookback. Wire cost is string-heavy, since every sample repeats resourceId, key and value. Remote Write v2's symbol table interns strings across a request and is a material win for this shape specifically. Emit the metadata series on their own cadence and batch rather than folding them into every data request.

08Failure modes

Duplicate match during churn

When an attribute changes, the old series stays resolvable for the whole lookback window, so a group_left join sees two matches and fails the query with found duplicate series for the match group. This is the known sharp edge of the info-series pattern and has no clean fix, because Prometheus has no tombstone. Mitigate in the documented idiom:

max by (resourceId, if_alias, if_descr) (
  last_over_time(onms_resource_info[10m])
)

09Cutover, not migration

This design is implemented as a greenfield label schema. There is no compatibility mode for the v0.x schema, no dual emission, and no read-path support for the old prefixes. The data series lose if_descr and every onms_attr_*, onms_extattr_* and onms_cat_* label, which changes the identity of every affected series once, at cutover. That is the cutover, and the design does not soften it.

Consequences to state in the release note, once. Series written before the cutover keep their old identity for the retention window and are not joined to the new ones. Dashboards that filtered on a removed label move to the group_left idiom of §06. OpenNMS graph rendering is unaffected across the boundary, because the read path resolves resources by __name__ and resourceId, both of which stay.

10Alternatives considered

The three candidate homes for a mutable attribute differ in exactly one observable way, and it shows up the moment an operator edits an interface description.

  • Columns only, with an allowlist. Rejected because it makes the allowlist load-bearing for read-path correctness, and because it cannot hold the long tail under the per-series label cap.
  • A relational side table. Rejected because it puts a database on the write path, makes the metadata unreachable from PromQL, and requires the read path to enrich every result from a second store. Its genuine advantage is that a mutable attribute changes nothing at all rather than forking a small series.
  • Deriving the column series with a recording rule. Rejected because it makes the mandatory query interface depend on an optional backend component, and because it means an operator configures two systems where one would do. Retained as an escape hatch.
What would still flip the whole design: if nobody queries the long tail and read-path parity is not required, columns-only with a modest allowlist is genuinely simpler. That is a testable question, not an architectural one. Look at what existing graph definitions dereference and what operators filter on in Grafana today. If that set is small, closed and stable across deployments, build the simple thing.

11Decisions

The four questions the first draft left open, resolved on 2026-09-14.

ifAlias placement is a principle, not a measurement

The draft wanted ifAlias churn measured before fixing its placement. It cannot be measured where the project measures everything else, since the reference fleet is simulated and its aliases never change, and the OpenNMS database holds only the current snmpinterface.snmpifalias with no history. More to the point, the number would not change the answer: an operator who has just relabelled an interface is the one about to look at its graph, and a low churn rate makes that split rarer, not acceptable. ifAlias and ifDescr stay in rows on principle (§01). Churn, once an operator measures it with two snapshots of snmpinterface weeks apart, tunes the re-emission cadence and the duplicate-match window, nothing else.

Default columns and budget

info.columns takes column=key entries and defaults to if_alias=ifAlias, if_descr=ifDescr, resource_name=name; resourceId is always present as the join key. Columns exist for attributes that are not on the data series, so the default does not mirror node_label or if_name. Sub-resource names under collector-specific keys such as hrStorageDescr, dskPath or datname are one config entry away, deliberately: a fixed "first key that looks like a name" rule was considered and rejected, because that list is collector-specific and would be wrong somewhere. The per-resource attribute budget defaults to 16, lowest keys kept, remainder counted.

Read path: one batched query, no plugin cache

OpenNMS reads external tags from the Metric objects that findMetrics returns; getTimeSeriesData rebuilds its Metric from the query response and needs none. So enrichment happens in one place, and it is one instant query per findMetrics call, not one per metric: last_over_time(onms_resource_attr{resourceId=~"^(…)$"}[2 × cadence]) over the call's resource set, batched by read.discovery-batch-size as the two-phase discovery path already does. The selector always carries the resource list, so it never selects the whole attribute space (§07). No plugin-side cache: OpenNMS already runs timeseriesSearcherCache in front of findMetrics, so a second cache would serve a stale alias for its TTL after exactly the operator action this design exists for. A bounded TTL cache with TTL equal to the cadence is the fallback if a deployment shows the second query dominating findMetrics latency, added on measurement.

Provenance. This design derives from Prometheus's own conventions for carrying entity metadata, specifically the info-series pattern used by kube-state-metrics and OpenTelemetry's target_info, and from the Remote Write specification. The relational side table appears above only as a rejected alternative, described at the level of externally observable architecture. No implementation detail of any AGPL-3.0 project informs this design. See CLAUDE.md for the project's clean-room constraint.
