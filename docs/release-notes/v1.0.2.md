A correctness release for the resource metadata series. If you run the metadata series on a fleet of any size, this one matters: on the reference fleet it removes about half of the largest metric in the backend and roughly 30,000 samples per second of avoidable write load.

No configuration keys change meaning, no wire format changes, no on-disk format changes. Upgrading is a KAR swap.

## What was wrong

OpenNMS attaches a meta tag to each metric whose key is that metric's identity: `ICMP/<ip>` for latency, `SNMP_<oid>.<ifIndex>` for a collected OID, a dotted bean path for JMX. The plugin read those as attributes of the *resource*, so a resource's metadata changed with whichever of its metrics was collected last (#223).

Two things followed from that one mistake:

- **`metadata.cadence-ms` had no effect at any value but `0`.** Every observation looked like a change, so every metadata series was re-emitted on every sample. Setting the cadence to 24 hours changed nothing.
- **`onms_resource_attr` grew without limit**, one key per interface per OID. `metadata.attr-budget` could not contain it: the budget caps one snapshot, which holds a single metric's two or three keys, while the union across a resource's metrics is what reached the backend.

Measured on an 11,000-device fleet with 144 interfaces each: 12,631 distinct attribute keys, 9,639,272 `onms_resource_attr` series (29% of the backend's total, about half of it metric identity), and about 30,000 metadata samples/s that took `store()` from 0.2 ms to about 5 ms and made OpenNMS's own ring buffer discard about 25,000 collected samples/s before the plugin ever saw them.

## What changed

A key is read as a resource attribute only when it is shaped like an OpenNMS collector alias: letters, digits, `_` and `-`, at most 64 characters. Anything else is one metric's identity and reaches no series. Every key the shipped `metadata.info-columns` reads is unaffected: `ifAlias`, `ifDescr`, `ifName`, `name`, `hrStorageDescr`, `dskPath`, `datname`, `spcname`.

**If you set `metadata.cadence-ms=0` to work around this, you can turn the metadata series back on.**

## After upgrading

Check `metadata_resource_changes_total`. It counts the observations that found a resource new or changed: a burst while resources are first seen, then near zero. A sustained rate near your sample rate means the cadence still is not binding, and the plugin now logs one WARN every ten minutes naming a resource and the attribute keys that differ.

Two new keys correct the rule without waiting for a release, both comma-separated globs and both empty by default:

- `metadata.attr-include` admits keys the shape rule rejects, for an OpenNMS that names an attribute unlike an alias. If a graph placeholder stops resolving after this upgrade, take the key from the placeholder itself and admit it.
- `metadata.attr-exclude` drops keys it admits, for a collector whose per-metric keys happen to be alias-shaped.

Neither can put a credential-shaped key, a context key, or a key with a series of its own on the wire, and `metadata.info-columns` is validated against both.

## Sizing: count resources, not devices

This fix removes the identity keys. It does not change how many resources you have, and that is what sets the floor. OpenNMS gives one SNMP interface a resource path per collection group, so an interface collected for traffic, packets and errors is three `resourceId` values, and the metadata series are per `resourceId` because that is the join key the data series carry.

The fleet above has 1.58 M interfaces and about 4.8 M resources, so one genuine attribute per resource is still about 4.8 M rows and, at the default 15-minute cadence, about 5,300 samples per second. The Sizing section of the documentation now states this arithmetic.
