An overload release. Everything in it comes from one benchmark run in which the plugin was handed about 64,000 samples a second, delivered a third of them, and could account for a quarter of what it lost. The counter that undercounted is fixed, sharded pipelines stop throwing away work for shards that had room, and the plugin now measures and publishes enough about its own write path that the next such run is a read of counters rather than a reconstruction.

Two things to check before upgrading: **`samples_dropped_queue_full_total` will rise** on any site that was already overloaded, and **a `store()` call can now be partially accepted and still throw.**

## Upgrade notes

**The queue-full counter now means samples** (#154). It used to count one per rejected `store()` call. OpenNMS hands the plugin about four samples per call under load, so the old reading was roughly a quarter of the real loss. Nothing is delivered differently; the number is honest now. Alert rules on `rate(samples_dropped_queue_full_total[5m]) > 0` fire exactly as before.

**`store()` is best-effort in queue mode** (#156). With `writer.shards > 1`, the first sample that met a full shard used to end the call, and every later sample was lost, including ones routed to shards with capacity. The call now attempts every sample, counts the refused ones, and throws once with `refused R of N sample(s)` in the message. Horizon's default ring-buffer writer drops the call on exception either way, so it simply sees more delivered.

**If you run Horizon's offheap writer** (`org.opennms.timeseries.config.buffer_type=OFFHEAP`), nothing to do on Horizon: it retries a whole call until accepted, so partial acceptance would make it re-send samples the plugin already took. The new key `queue.store-policy` defaults to `auto`, which detects that writer and gives it `all-or-nothing`: the call is refused whole, without enqueuing anything, when any shard lacks room. On **Sentinel** the buffer type lives in ConfigAdmin rather than a system property, so `auto` resolves to `partial`; set `queue.store-policy = all-or-nothing` explicitly there. The resolved policy is logged at activation.

**New MBeans appear in the Karaf JVM** under `org.opennms.plugins.prometheus.remotewriter`. If you already run a JMX exporter against OpenNMS, add the rule from the operations guide and the plugin's counters become time series.

## Highlights

**Sharded pipelines no longer lose work to head-of-line rejection** (#156, #158). One saturated shard discarded samples bound for N-1 shards that could have taken them, which defeated `writer.shards` under exactly the load it exists for. Refusals are counted per sample and one exception is built per call, not per refused sample: at benchmark load that is tens of thousands of stack traces a second not constructed.

**The plugin can now explain its own throughput** (#155, #159). Six new measurements, all plain counters and gauges:

| Name | Answers |
|---|---|
| `http_write_duration_ms_total` | Mean round-trip and flusher utilisation, with the write counts |
| `flusher_idle_ms_total` | Whether the flusher was waiting or busy |
| `store_calls_total`, `store_calls_failed_total` | Caller-side call and failure rates |
| `store_samples_offered_total` | Offered versus written versus dropped, from the plugin alone |
| `samples_dropped_unmapped_total` | Samples with no metric name, previously skipped silently |
| `queue_depth_high_water` | The peak the queue reached, not the depth at the moment you looked |

**Metrics are scrapable over JMX** (#155). The operations guide had said they were; nothing implemented it. The registry was private and no reporter was attached, so a JMX exporter saw JVM metrics and none of the plugin's. Every counter and gauge is now an MBean while the plugin is active, and the guide shows the one `jmx_exporter` rule that covers all of them.

## Fixes

- `samples_dropped_queue_full_total` counts every sample a refused `store()` call carried, not one per call (#154, #157).
- The documented sizing advice that tied queue capacity to the offheap writer's batch size was wrong and is gone; that setting sizes its on-disk block, not the list handed to the plugin (#158).
- The docs install snippet resolves its version attributes again (#153).
