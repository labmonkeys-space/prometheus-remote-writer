A durability release. The plugin no longer refuses samples when its memory queue fills — every shard now has a durable bucket on disk behind it, so a backend outage becomes a delivery delay rather than data loss, bounded by a budget you set. The Write-Ahead Log this replaces was an either/or alternative to sharding; the tier sits behind it, so throughput and durability finally combine.

Three things to do before upgrading: **rename your `wal.*` keys**, **drain any existing WAL directory**, and **check your backend's ingest limits** — the default shard count goes from 1 to 4.

## Upgrade notes

**The `wal.*` keys are gone, with no aliases.** Leftover lines in an existing `.cfg` are inert rather than an error, which means an upgrade that ignores this section starts cleanly and quietly runs a different configuration than intended. The mapping:

| 0.7.x | 0.8.0 |
|---|---|
| `wal.enabled = true` | a non-zero `overflow.max-size-bytes` — now the default |
| `wal.enabled = false` | `overflow.max-size-bytes = 0` |
| `wal.path` | `overflow.dir` |
| `wal.max-size-bytes` | `overflow.max-size-bytes` |
| `wal.segment-size-bytes` | removed — derived as an eighth of a shard's slice |
| `wal.fsync = never` | `overflow.fsync = none` |
| `wal.overflow = backpressure` | `overflow.full = refuse` |
| `wal.overflow = drop-oldest` | `overflow.full = drop-oldest` |
| `samples_dropped_wal_full_total` | `samples_dropped_overflow_full_total` |

**Drain the 0.7.x WAL before upgrading.** Its on-disk layout is a single log at the root of `wal.path`; 0.8.0 reads one subdirectory per shard and will not find it. Segments left behind are not migrated and not reported — they are simply never shipped. Let the WAL empty, confirm `wal_replay_samples_total` is not moving, then upgrade.

**The write-path defaults moved**: `writer.shards` 1 → 4, `queue.capacity` 10000 → 40000, `batch.linger-ms` 0 → 100. This changes behaviour on a deployment that edits no configuration at all.

- **Four concurrent streams to the backend where there was one.** Check per-tenant ingest limits on Mimir and on VictoriaMetrics cluster before upgrading. Set `writer.shards = 1` to keep the old behaviour.
- **Per-shard gauges start appearing** — `shard_<i>_queue_depth`, `shard_skew_pct`, `overflow_pending_samples_shard_<i>` — because they are registered only when sharding is on. Dashboards that enumerate metric names will see new series.
- **The memory buffer quadruples**, from 10,000 samples to 40,000, single-digit MB at typical label sets.

The activation log now names the whole resolved write path on one line, so what a deployment actually got after the upgrade is one grep rather than seven keys inferred:

```
write path: writer.shards=4, queue.capacity=40000 (10000 per shard), batch.size=1000,
batch.linger-ms=100, overflow=4294967296 bytes (1073741824 per shard),
overflow.drain=ordered, overflow.full=refuse, queue.store-policy=partial (auto: ...)
```

**A disk tier is now on by default and needs a writable directory.** `overflow.dir` blank resolves to `${karaf.data}/prometheus-remote-writer/overflow`. Under containerised Karaf with an ephemeral `${karaf.data}` that evaporates on restart, which is worse than useless — point it at a mounted volume. If a deployment should stay diskless, set `overflow.max-size-bytes = 0` and it behaves exactly as 0.7.x did: a full queue refuses.

## Highlights

**A full memory queue spills to disk instead of refusing** (#165). Zero loss now has a stated bound rather than being a hope: `overflow.max-size-bytes` divided by the offered rate is how long the backend can be down before the plugin starts refusing. At 64,000 samples/sec and roughly 60 bytes a sample, the shipped 4 GiB buys on the order of 15 to 20 minutes.

The ordering rule underneath is worth knowing, because it explains the shape of everything else. A queue spills because it is *full*, so at that moment memory holds the **older** samples. Putting only the refused one on disk would send it ahead of them, since the bucket drains first. So the transition moves the shard's whole memory backlog to disk, and everything after it goes there too until the bucket empties. Memory is therefore empty for the entire spilling period — which makes disk-before-memory drain trivially correct, and means every batch sent during an outage is a disk batch, retried rather than dropped.

**Sharding and durability combine** (#165). The WAL was a single ordered log, so `writer.shards > 1` was rejected outright with it enabled. Each shard now owns its own bucket and its own ordered log.

**`overflow.drain = ordered | concurrent`** (#166). `ordered` (default) is correct on every backend. `concurrent` keeps using memory while the bucket drains and alternates the tiers, so a sample offered a second after the backend recovers does not wait out the whole backlog — at the cost of per-series order across the tier boundary, so it needs a backend that accepts out-of-order writes. See the per-backend table in the operations guide; Mimir qualifies only inside its configured out-of-order window.

**End-to-end latency is measured** (#164). `sample_latency_ms_total` sums each written sample's age at backend acknowledgement, so mean end-to-end latency is that over `samples_written_total` — the number a latency budget is actually stated in. It covers queue wait, linger, build, round-trip, and time on disk, counted from the original `store()` even across a restart.

**Each shard builds the next request while the previous is in flight** (#163), and **series identity is computed once per sample** (#164). On the benchmark fleet a shard's cycle was about 11 µs of build plus 5 µs of round-trip per sample, serial; it is now the larger of the two. The per-sample key work that was 17% of build time happens once, when the sample is mapped.

**`batch.linger-ms`** (#162). At four shards on an 11,000-device fleet, a linger of 0 produced 3,300 requests a second of 19 samples each. The new default of 100 ms trades a tenth of a second for full batches.

## New metrics

| Name | Answers |
|---|---|
| `sample_latency_ms_total` | Mean end-to-end latency, over `samples_written_total` |
| `samples_spilled_total` | How much went to disk, including the backlog moved at the transition |
| `samples_drained_from_overflow_total` | How much came back off it |
| `samples_dropped_overflow_full_total` | What was refused with both tiers full |
| `samples_evicted_overflow_total` | What `drop-oldest` discarded |
| `overflow_pending_samples` | Backlog depth, total and per shard |
| `overflow_bytes` | Disk used, against the budget |
| `overflow_recovering_shards` | How many shards are draining a backlog |
| `overflow_oldest_pending_age_ms` | **The recovery alert.** How far behind the tier is, in the unit the budget uses |
| `flusher_build_ms_total`, `http_writes_{4xx,5xx,transport}_total`, `http_write_duration_bucket_le_*` | Build share, error rate as a request ratio, round-trip distribution |

Depth and age answer different questions. A backlog of 200,000 samples is only alarming relative to the drain rate; an oldest sample twelve minutes old is alarming on its own. Alert on the age.

## Known limits

**Picking `concurrent` on a backend that rejects out-of-order writes fails quietly.** The backend answers 4xx, `samples_dropped_4xx_total` climbs, and nothing names the cause. `ordered` is the default and the docs carry a per-backend table; there is no automatic fallback.

**`drop-oldest` discards data the backend has not acknowledged.** That is the point of it — sparing unacknowledged data would make the policy inert during an outage, when the checkpoint is frozen and every surviving segment sits above it. `refuse`, the default, spares everything unacknowledged and pushes the decision back to OpenNMS.

**`overflow.max-size-bytes` is split evenly across shards**, so hash skew applies to disk exactly as it does to memory: one hot shard can exhaust its slice while its siblings idle. Watch `overflow_pending_samples_shard_<i>`, not only the total.

**`wal_replay_samples_total` is approximate.** It sums per-segment index counts, which over-count a segment spanning the checkpoint and under-count one whose index lagged its last append. Read it as "recovery found work"; it is deliberately not a term in the reconciliation identity.

**Spill and drain are covered by integration tests against Prometheus only.** Mimir and VictoriaMetrics are exercised by the smoke suite's write path, which contains no spill.

## Fixes

- A batch drawn from the disk tier is no longer read ahead of the sender, which could let a rewind be undone by the next batch's acknowledgement advancing the checkpoint straight past it (#165).
- `overflow.fsync = batch` actually fsyncs on the flush-interval boundary; the call had no caller, making the real RPO the whole unflushed segment (#165).
- `overflow.full = drop-oldest` can evict during an outage. The eviction floor sat at the checkpoint, and everything below it was already collected, so nothing was evictable exactly when the policy was wanted (#165).
- A memory batch the backend refuses is taken onto disk and retried rather than dropped, so a sample is durable from the first failure and not only once the queue happens to fill (#165).
- `PluginMetrics.sampleLatency` no longer overflows `long` past about 5.3M samples in one batch, which silently discarded the result (#164).
