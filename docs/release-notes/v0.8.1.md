A fix release for the disk overflow tier that v0.8.0 introduced. **Every v0.8.0 deployment with the disk tier on should upgrade.** The tier is on by default.

No configuration keys, defaults, metric names, wire behaviour or on-disk formats change. Upgrading is a KAR swap.

## Fixes

**A shard that spilled to disk while running could stop writing until the process restarted** (#177). The v0.8.0 benchmark found it (#176). The shard's bucket then grew to `overflow.max-size-bytes` and refused, so a full memory queue ended in data loss rather than delay. The shipped defaults reach this through ordinary hash skew: the hottest shard fills its slice of `queue.capacity` first.

The cause was a race in how each shard's flusher counts the payloads between its builder and sender threads. A disk read waits for that count to reach zero. When the sender finished a payload before the builder had counted it, the count stuck at one, and every later disk read waited for a sender that was already idle. Only a restart reset it. The count is now taken before the sender can see the payload, and a live spill drains through the running flusher (#178).

**How to tell whether a v0.8.0 deployment is affected:** `overflow_recovering_shards` stays above 0 while `samples_written_total` is flat for that shard, and none of `samples_dropped_4xx_total`, `samples_dropped_5xx_total` or `samples_dropped_transport_total` is moving. `overflow_oldest_pending_age_ms` grows one for one with wall-clock time. Until you upgrade, a restart or a configuration reload drains the stuck bucket.

**A drain that cannot proceed is now logged.** When a disk read waits its full 30 s bound for the sender, the flusher logs at WARN:

```
<flusher-thread>: the overflow drain waited 30000ms for the sender to settle N payload(s) and is retrying. Expected while a write is retrying against a slow backend; with no write in progress the drain is stuck
```

It is expected while a single write retries against a slow backend, because the default `http.read-timeout-ms` alone equals the bound. Read it together with the write counters.

**The plugin's INFO lines are hidden on a stock Horizon, and the docs now say so.** Horizon sets `org.opennms` to WARN, which covers the plugin, so the `write path:` activation line that the v0.8.0 notes describe does not appear by default. The Log levels section of the documentation gives the override:

```
log:set INFO org.opennms.plugins.prometheus.remotewriter
```

## Known limits

- The #176 benchmark criterion "`overflow_recovering_shards` returns to zero after an induced overrun" has not yet been re-measured on v0.8.1. The fix is covered by deterministic tests and a shard-level spill-and-drain test under both drain policies, not yet by a fleet run.
- No real backend outage has been benchmarked against the tier yet. The v0.8.0 overruns came from shard count and hash skew with a healthy backend.
- Under `overflow.drain = ordered`, samples offered while a shard drains also go to its bucket. The shard returns to memory only when the reader catches up between two arrivals, so under sustained load a shard can stay on the slower disk path for a while after an overrun.
