A correctness release. No plugin behaviour changes: the wire format, configuration surface and label emission are identical to v0.6.0. Everything here is about constraints and published statements that described the Horizon 35 runtime v0.6.0 stopped supporting.

One thing to check before upgrading: **the KAR now requires a Java 21 runtime.**

## Upgrade notes

The plugin compiles to Java 21 bytecode, so its bundle declares `osgi.ee=JavaSE;version=21` and will not resolve on an older JVM.

If you are on a supported OpenNMS Horizon, **there is nothing to do.** Horizon 36.0.4 — the minimum since v0.6.0 — runs OpenJDK 21:

```bash
docker run --rm --entrypoint sh opennms/horizon:36.0.4 -c 'java -version'
# openjdk version "21.0.12.1" 2026-08-18 LTS (Red_Hat-21.0.12.1.1-1)
```

If you run Horizon in a custom image with an older JVM, the feature will fail to resolve at install time. That failure is visible and harmless: `karaf.log` records the unsatisfied `osgi.ee` requirement, no samples are written, and the previous KAR can be redeployed.

The target had been held at Java 17 to match the Horizon **35** container, whose JVM was 17. Raising the support floor to 36.0.4 in v0.6.0 retired that constraint, and a pin whose stated reason has expired is one nobody can reason about safely.

## Highlights

**The published compatibility table was wrong in every row, and now is not.** It is the table users act on, and it had drifted from the runtime it describes:

| Row | Said | Actually |
|---|---|---|
| OpenNMS Horizon | 35+ | **36.0.4+** |
| JVM | Temurin / OpenJDK 17 | **OpenJDK 21** (a Red Hat build, not Temurin) |
| Apache Karaf | 4.4.11 | **4.4.9** |
| Integration API | v2.0 | **`[2.0.1,3.0.0)`** |

Each row is now a property of the oldest supported Horizon container, with the command that observes it recorded beside the value so it can be re-run at the next floor bump.

**A build property could silently rewrite a documented figure.** The Karaf row is the reason the whole table was audited. The docs source said `4.4.x`; the published page said `4.4.11`. asciidoctor-maven-plugin exposes Maven project properties as AsciiDoc attributes with dots converted to dashes, and those *outrank* attributes declared in the document — so `karaf.version` (a build dependency) replaced the documented value with no error, no warning and no visible diff.

The effect was to publish a **build-time version as a runtime requirement**, and one *newer* than the supported container provides. A reader would have concluded they needed Karaf 4.4.11 when Horizon 36.0.4 ships 4.4.9. The attributes are renamed out of the Maven property namespace, so the collision is now impossible rather than merely corrected.

## Fixes

- Removed the `org.osgi.framework` and `org.osgi.service.cm` `Import-Package` overrides. Both were pinned for Felix 6.0.5 on Horizon 35; Horizon 36.0.4 ships Felix 7.0.5 exporting `org.osgi.framework` 1.10 and configadmin 1.9.26 exporting `org.osgi.service.cm` 1.6.0, so the computed ranges resolve unaided. The `org.slf4j` override is kept — the container really does ship `slf4j-api-1.7.36` — with its rationale corrected.
- The README compatibility table carried the same JVM and Karaf errors as the docs site and was fixed in the same change, so the two cannot diverge.
