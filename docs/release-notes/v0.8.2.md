An operational release for the disk overflow tier. It corrects the sizing guidance, documents what a backend outage costs OpenNMS's writer threads, and makes `store()` cheaper while a shard spills to disk.

No configuration keys, defaults, metric names, wire behaviour or on-disk formats change. Upgrading is a KAR swap.

## Check your disk budget

**The sizing guidance overstated the outage window nearly six times** (#181). The 0.8.x docs, the shipped `.cfg` comment and the 0.8.0 release notes said a sample takes about 60 bytes on disk, so the default 4 GiB would buy 15 to 20 minutes at 64,000 samples/sec. A bucket stores every sample's metric name and labels uncompressed, so the real figure depends on your label set. A native-profile OpenNMS fleet measured about 340 bytes, which makes the default **about 3 to 4 minutes** at that rate. Tolerating 15 minutes there needs about 18 GiB.

If you sized `overflow.max-size-bytes` from the old figure, re-check it. Measure your own bytes per sample during an outage:

```
bytes_per_sample = (overflow_bytes - overflow_bytes at 0 pending) / overflow_pending_samples
```

The baseline matters because a drained bucket keeps its newest segment, acknowledged bytes included, and those bytes count against the budget. After an earlier spill, the next outage window can be up to an eighth shorter. The Sizing section of the documentation has the details.

## Highlights

**`store()` is cheaper while a shard spills to disk** (#182, #184). A spilled sample used to hold its shard's lock for a protobuf encode, a CRC and about four syscalls, and near the budget cap for a directory listing on every append, refused ones included. Now a call's samples are grouped by shard and each shard's lock is taken once per call. The frames are encoded before the lock, and an append is one positional write. Nothing on the append path lists the bucket directory, and a periodic fsync no longer holds the lock appends need. Where each sample lands is unchanged, which a property test checks against one-at-a-time placement.

On a local benchmark (64 threads, 4 shards, 4 samples per call, macOS) the disk path went from 206,000 to 314,000 samples/sec and the memory path from 715,000 to 1,603,000. These are local figures; a fleet measurement of this release is still to come.

**The docs now say what a backend outage costs OpenNMS's writer threads** (#182). A spilling shard slows `store()`, and when the writer threads cannot keep up, Horizon's ring buffer discards samples the plugin never sees. On the reference fleet under 0.8.1, a 5-minute outage took mean `store()` time from 0.7 ms to 4.7 ms, then 7.7 ms during the drain. OpenNMS discarded 12.9 million samples, 21 times what the plugin refused.

- Under `overflow.drain = ordered` the slow path lasts until the bucket is empty, not until the backend returns.
- If your writer threads cannot absorb that and your backend accepts out-of-order writes, `concurrent` keeps new samples on the memory path during the drain.
- To account for an outage, read OpenNMS's `ring-buffer.dropped-samples` meter (JMX domain `org.opennms.timeseries`) alongside the plugin's counters.

## Fixes

- A segment write that fails partway, for example on a full disk, is cut back to the segment's logical end, so a sealed segment can no longer hold a torn tail that sends the reader into the next one (#184).

## Known limits

- The disk path is still slower than memory: the local gain is 1.5 times, not the 2 times aimed for. Batching the per-frame writes is the next step, pending a fleet rerun of the #182 outage on this release.
- The #176 recovery criterion (`overflow_recovering_shards` back to zero after an induced overrun) has still not been re-measured on the fleet.
