[#overflow]
= Disk overflow tier

Every shard has a memory queue and, behind it, a durable bucket on disk.
In normal running only the queue is used. When the queue fills, the shard
spills to its bucket instead of refusing the sample, so a backend outage
becomes a delivery delay rather than data loss — for as long as the bucket
has room.

Configured by default with a 4 GiB budget. Set
`overflow.max-size-bytes = 0` to switch it off and get the pre-0.8.0
behaviour, where a full queue refuses with a `StorageException`.

== What the tier gives you

* *Zero loss with a stated bound.* Nothing is refused until the disk budget
  is exhausted. Divided by the offered rate, `overflow.max-size-bytes` is
  how long a backend can be down before the plugin starts refusing.
* *Restart preservation.* Samples on disk at shutdown ship on the next
  start, ahead of anything offered after it. Under the default `batch`
  fsync a `kill -9` may lose the last fsync window; everything before it is
  durable.
* *Sharded throughput and durability together.* Each shard owns its own
  bucket, so `writer.shards > 1` and a disk tier combine. Before 0.8.0 the
  WAL was one ordered log and forced `writer.shards = 1`.

== How the tiers relate

The rule is short: *while a shard's bucket holds anything, that shard's
memory queue is empty.*

[.text-center]
....
  store(sample) ──▶ bucket non-empty? ──yes──▶ bucket.append
                          │ no
                          ▼
                    queue.offer ──ok──▶ done
                          │ full
                          ▼
                    move the whole queue into the bucket,
                    in order, then append this sample
....

The backlog moves rather than staying behind because a queue fills from the
front: at the moment of the spill, memory holds the *older* samples.
Appending only the refused sample would put it on disk ahead of them, and
the bucket drains first — so a series would arrive out of order and the
backend would reject it.

Three things follow from moving it, and they are the reason for the rule
rather than side effects:

* Disk-before-memory drain is offered order, trivially, because memory is
  empty for the whole spilling period.
* Every batch sent during an outage is a disk batch. A disk batch the
  backend refuses is retried, never dropped — so zero loss does not depend
  on which tier a sample happened to land in.
* The batch already in flight when the outage starts is not an exception:
  a memory batch the backend refuses is taken onto disk and retried rather
  than dropped, so a sample is durable from the first failure and not only
  once the queue happens to fill.
* A shard is either memory-only or disk-only. No request ever mixes the
  two, and there is no mixed state to reason about.

The cost is one bulk transfer at the transition, bounded by
`queue.capacity / writer.shards`.

== Drain policy

`overflow.drain` decides how a shard divides its drain between the two
tiers. It is not only a drain-side setting: under `ordered` the *accept*
path keeps the memory queue empty while the bucket is non-empty, which is
what makes disk-before-memory equal offered order. `concurrent` changes
both ends.

[cols="1,2,2",options="header"]
|===
| | `ordered` (default) | `concurrent`

| Accept with a non-empty bucket
| goes to the bucket
| goes to memory while it has room

| Memory queue fills
| the whole backlog moves to the bucket
| only the refused sample is appended

| Drain
| bucket to empty, then memory
| the tiers alternate

| Per-series order across the boundary
| preserved
| not preserved

| Fresh-sample latency during a recovery
| behind the whole backlog
| roughly one batch

| `store()` cost during a drain
| disk path until the bucket is empty
| memory path while memory has room

| Time to clear the backlog
| baseline
| about twice as long
|===

`ordered` is correct on every backend. `concurrent` needs one that accepts
out-of-order writes, and choosing it wrongly is a quiet failure: the
backend answers 4xx, `samples_dropped_4xx_total` climbs, and nothing says
"wrong drain policy".

[cols="2,1,3",options="header"]
|===
| Backend | Safe policy | Note

| Prometheus
| `ordered`
| Rejects a sample older than the newest it holds for that series.

| Mimir
| `ordered`, or `concurrent` inside its window
| Only if `-ingester.out-of-order-time-window` is configured and your
  backlog fits inside it. A recovery longer than the window is rejected.

| VictoriaMetrics
| either
| Accepts out-of-order writes by design.

| Cortex
| `ordered`
| Same model as Prometheus unless out-of-order ingestion is enabled.
|===

Alternating rather than draining memory first is deliberate. Memory-first
minimises fresh-sample latency, but a bucket then never empties while the
offered rate matches the drain rate: the backlog becomes permanent and the
outage window quietly shrinks to nothing. Alternating bounds how long the
backlog lives and keeps `overflow_oldest_pending_age_ms` a number that
comes back down.

[#overflow-caller-cost]
=== What an outage costs the writer threads

A sample bound for disk costs `store()` more than one bound for memory, because it is written to the bucket while its shard's lock is held.
So a spilling shard slows the OpenNMS writer threads that call it, and when they cannot keep up, OpenNMS discards samples before they reach the plugin.
None of the plugin's counters include those; <<operations,Operations>> names the OpenNMS counter that does.

During the outage itself both policies spill, since memory cannot drain either.
The difference is the drain.
Under `ordered`, every new sample for a recovering shard keeps going to disk until its bucket is empty, so the slow path lasts until the backlog is gone, not until the backend returns.
The cost outlasts the outage by the length of the drain.

#182 measured this on 0.8.1: 11,000 devices offering about 64,000 samples/sec, a backend cut off for 5 minutes, shipped defaults.
Mean `store()` time was 0.7 ms before the outage, 4.7 ms during it and 7.7 ms during the drain.
OpenNMS's ring buffer discarded 12.9 million samples, 21 times the 612,639 the plugin refused, and the writer threads stayed slow for 8.5 minutes.
The disk path has been made cheaper since, but it is still slower than memory, so the shape holds.

If your writer threads cannot absorb that, and your backend accepts out-of-order writes, use `concurrent`.
It keeps new samples on the memory path while the bucket drains, so `store()` returns to its normal cost as soon as memory has room rather than when the backlog is gone.
The price is per-series order across the tier boundary, as the table above says.

== Configuration

[cols="2,1,4",options="header"]
|===
| Key                          | Default | Purpose

| `overflow.dir`               | `""` | Empty resolves to `${karaf.data}/prometheus-remote-writer/overflow`. One subdirectory per shard. Set explicitly to redirect to a mounted volume or faster disk.
| `overflow.max-size-bytes`    | `4294967296` (4 GiB) | Total budget across every shard's bucket, split evenly at startup. `0` disables the tier entirely.
| `overflow.full`              | `refuse` | `refuse` = the append is refused, counted, and `store()` throws; `drop-oldest` = evict the oldest whole segment and accept.
| `overflow.fsync`             | `batch` | `always` = fsync every append (tightest RPO); `batch` = fsync at each `flush.interval-ms` boundary (loses at most that window on `kill -9`); `none` = OS page cache only.
| `overflow.drain`             | `ordered` | `ordered` = bucket drained to empty before any memory sample, per-series order preserved; `concurrent` = tiers alternate, needs a backend that accepts out-of-order writes. See the table above.
|===

Segment size is derived, not configured: each bucket holds eight segments,
so `drop-oldest` evicts an eighth of a shard's budget rather than the lot,
and the segment count per shard does not grow with `writer.shards`.

[#overflow-sizing]
== Sizing

----
outage_window = overflow.max-size-bytes / (samples_per_second × bytes_per_sample)
----

`bytes_per_sample` depends on your label set, so measure it rather than assume it.
Every frame in a bucket stores one whole sample: an 8-byte header, the timestamp, the value, the metric name, and every label key and value as a string.
Nothing is shared between frames and nothing is compressed, so the labels are most of the size.
The snappy-compressed wire payload is no guide to it.

Measured on a native-profile OpenNMS fleet of SNMP interface data, a sample takes about 340 bytes on disk.
At 64,000 samples/sec that is about 22 MB/s, so the default 4 GiB buys about 3 to 4 minutes of backend outage.
The formula gives 3.3 minutes, and a real outage on that fleet ran 4.2 minutes from cut-off to the first refusal.
Tolerating 15 minutes at that rate needs about 18 GiB.

To measure your own figure, note `overflow_bytes` while `overflow_pending_samples` is 0, then read both gauges again while a bucket is filling during an outage:

----
bytes_per_sample = (overflow_bytes - overflow_bytes at 0 pending) / overflow_pending_samples
----

Both gauges are exported over JMX.
The baseline matters because a drained bucket keeps its newest segment, acknowledged bytes included, until the writer moves on to a new one.
That can be up to an eighth of a shard's slice, 128 MiB with the defaults, so a plain ratio early in a spill can read several times too high.
On a fresh install with empty bucket directories the baseline is 0.
Those leftover bytes also count against the budget, so after an earlier spill the next outage window can be up to an eighth shorter.

Do not take the reading while a bucket drains.
Pending samples fall as batches are acknowledged, but a segment is released only once the backend has taken all of it, so the ratio reads high.

The window bounds what the plugin refuses, not what the caller loses: a spilling shard also slows `store()`, and OpenNMS discards what its writer threads cannot hand over (<<overflow-caller-cost,What an outage costs the writer threads>>).

The budget is split evenly across shards, so hash skew applies to disk just as it does to memory.
The hottest shard fills its slice first, and it is that shard's slice and its share of the rate that set the window.
Watch `overflow_pending_samples_shard_<i>`, not only the total.

== How it works, briefly

[.text-center]
....
  store(samples)
      │
      ▼
  LabelMapper.map()
      │
      ▼
  Shards.accept()  ──▶  memory queue  ─┐
      │ (spilling)                     │  bucket empty
      ▼                                ▼
  bucket.append(MappedSample)   ──▶  builder ──▶ sender ──▶ HTTP POST
      ◀── durable on disk                                      │
                                                     2xx ──────┤
  disk batch:  checkpoint.advance(offset), segments released   │
  4xx:         advance too — the backend will never take them  │
  5xx / transport: leave the checkpoint, re-read next cycle ◀──┘

  memory batch: 2xx counts written; 5xx exhausted or transport hands the
  batch to the bucket and retries it from there. Only with no disk tier
  configured is there nowhere to put it back, and only then is it dropped.
....

Segment files are named by start offset
(`00000000000000000000.seg`, ...), each with a companion `.idx` summary.
`checkpoint.json` in the shard's directory tracks the last offset confirmed
shipped, written atomically (tmp + fsync + rename) on every advance.

== Watching a recovery

`overflow_pending_samples` says how much is waiting. `overflow_oldest_pending_age_ms`
says how far behind the tier is, in the same unit the latency budget is
written in — that is the one to alert on. A backlog of 200,000 samples is
only alarming relative to the drain rate; an oldest sample 12 minutes old
is alarming on its own.

`overflow_recovering_shards` says how many shards are draining. With hash
skew it is often 1 of 4, which is a different problem from all 4 — the
first is one hot series set, the second is a backend that went away.

== Recovery on startup

Each shard scans its own subdirectory and replays anything past its
`checkpoint.json`. A shard whose bucket recovers non-empty starts out
spilling, so recovered samples ship before anything offered after the
restart. Recovery tolerates *torn tails* — an incomplete frame at the end of
the newest segment, typical of a process killed mid-append — by logging a
WARN, truncating to the last good frame, and resuming.

An enqueue timestamp rides in each frame, so a replayed sample's
`sample_latency_ms_total` contribution counts from its original `store()`
call rather than from the replay.

If recovery fails (unwritable path, corrupt `checkpoint.json`, unreadable
segment), the plugin refuses to start with an error naming the file and the
reason. Reset by removing the directory while the plugin is stopped:

[source,bash]
----
# while the plugin is stopped
rm -rf ${overflow.dir}
----

The plugin recreates it on next start.

== Wire-version interaction

The tier stores `MappedSample` (pre-wire). Flipping `wire.protocol-version`
while a bucket holds pending samples is safe — the next flush emits in the
new version, with no migration step. See <<wire-protocols>>.

== Operational guidance

[cols="1,4",options="header"]
|===
| Choice            | When

| `overflow.fsync=always`
| You can justify the ~10× throughput hit for tighter-than-1s RPO. Rare.

| `overflow.fsync=batch` (default)
| The right choice for almost everyone. Loses at most one
  `flush.interval-ms` window on `kill -9` / power loss.

| `overflow.fsync=none`
| Ephemeral deployments that accept losing in-flight data on kernel panic
  or power loss.

| `overflow.full=refuse` (default)
| Alerting-driven pipelines that want an operator to see the failure when
  the backend has been unreachable longer than the budget allows. Silent
  loss should be a deliberate choice.

| `overflow.full=drop-oldest`
| Dashboards showing "the last N hours" — recency over history; tolerates
  silent eviction of the oldest samples better than a `store()` exception.
  Note that eviction discards the oldest segment whether or not the backend
  has taken it: during an outage the checkpoint is frozen, so refusing to
  evict unacknowledged data would make the policy a no-op exactly when it is
  needed. The shard moves its reader past the hole and carries on with the
  newest data.

| `overflow.max-size-bytes=0`
| A local backend on the same box that is effectively always up, or a test
  environment where disk I/O for samples that will certainly deliver is
  pure overhead.
|===

[WARNING]
.Containerised Karaf
====
If `${karaf.data}` is ephemeral (a container with no mounted volume), the
default `overflow.dir` evaporates across restart and the tier is worse than
useless. Set `overflow.dir` explicitly to a mounted volume.
====

== Self-metrics

The tier adds these (visible via `opennms:prometheus-writer-stats`):

* `samples_spilled_total`
* `samples_drained_from_overflow_total`
* `samples_dropped_overflow_full_total`
* `samples_evicted_overflow_total`
* `overflow_pending_samples`, and `overflow_pending_samples_shard_<i>` per shard
* `overflow_bytes`
* `wal_replay_samples_total`, `wal_batches_dropped_4xx_total`

The general write counters (`samples_written_total`,
`samples_dropped_4xx_total`, `samples_dropped_5xx_total`,
`samples_dropped_transport_total`) are unchanged and continue to apply.
