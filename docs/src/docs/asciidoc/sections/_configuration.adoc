[#configuration]
= Configuration reference

All knobs live in `{cfg-file}` (Karaf ConfigAdmin PID `{cfg-pid}`) and
take effect on the next flush cycle — no OpenNMS restart required, except
where noted (typically wire-format and validator changes that require
bundle restart).

== Endpoint and authentication

[cols="2,1,4",options="header"]
|===
| Key                          | Default | Purpose

| `write.url`                  | _(required)_ | Remote Write v1/v2 ingest URL.
| `read.url`                   | _(required for read path)_ | Prometheus-compatible HTTP API root. The plugin appends `/api/v1/series` and `/api/v1/query_range` — do not include `/api/v1` here.
| `instance.id`                | _(unset)_ | Stamps every sample with `onms_instance_id="<value>"`. Required for multi-instance deployments sharing a backend.
| `job.name`                   | _(unset)_ | Override the per-sample `job` derivation with a fleet-wide constant.
| `tenant.org-id`              | _(unset)_ | Sets the `X-Scope-OrgID` header. Cortex/Mimir/VictoriaMetrics-cluster/Thanos partition by this.
| `auth.basic.username`        | _(unset)_ | Basic auth — username.
| `auth.basic.password`        | _(unset)_ | Basic auth — password.
| `auth.bearer.token`          | _(unset)_ | Bearer auth. Produces the same header as `auth.authorization.type = Bearer`; the two cannot both be set.
| `auth.authorization.type`    | _(unset)_ | Scheme keyword of a custom `Authorization` header — e.g. `Token` (InfluxDB v2) or `ApiKey` (Elasticsearch). Trimmed; casing preserved; no allowlist. Must be a single HTTP token. `Basic` is rejected. **Required** whenever credentials are set — there is no default scheme.
| `auth.authorization.credentials` | _(unset)_ | Credentials half of the custom `Authorization` header. Required whenever the block is used.
| `tls.ca-file`                | _(unset)_ | PEM bundle to trust in addition to / in place of the JDK truststore.
| `tls.insecure-skip-verify`   | `false`   | Disables hostname and certificate verification. Logs WARN on startup and every hour.
|===

NOTE: `auth.basic.*`, `auth.bearer.token` and `auth.authorization.*` each
produce the `Authorization` header, so they are mutually exclusive. The plugin
refuses to start if more than one is configured.

=== Custom `Authorization` schemes

Backends and gateways that authenticate with a non-standard `Authorization`
keyword are configured through the split `auth.authorization.*` block, which
emits `Authorization: <type> <credentials>` on the write path **and** the read
path:

[source,properties]
----
auth.authorization.type        = Token
auth.authorization.credentials = ${env:INFLUX_TOKEN}
----

The block is named after Prometheus's own `authorization: {type, credentials}`
and behaves the same way. The scheme keyword is emitted verbatim: leading and
trailing whitespace is trimmed, casing is preserved (`ApiKey` stays `ApiKey`),
and it is joined to the credentials with exactly one space. There is no
allowlist of known schemes — most backends this serves authenticate with an
unregistered keyword, so an allowlist would reject exactly the deployments the
block exists for.

Rules enforced at startup:

* `auth.authorization.type = Basic` (in any casing) is rejected. Basic
  credentials are built from a username and a password, so use
  `auth.basic.username` / `auth.basic.password`, which base64-encode them for
  you.
* Both keys are required together. `auth.authorization.type` has no default:
  an unset type with credentials set fails at startup by name. That is
  deliberate — a `Bearer` default would turn a typo'd
  `type = pass:[${env:NAME}]` into a plausible-looking wrong header, sending
  `Bearer <token>` to a backend expecting `Token <token>`: 401 forever, with a
  clean startup and a log line claiming authentication was configured.
* Both halves must be legal HTTP header content: no CR or LF, no non-printable
  or non-ASCII bytes. Note that leading and trailing whitespace is stripped
  before this check, so a credential read from a file that ends in a newline is
  accepted and the trimmed value is sent; only an *interior* CR or LF is
  rejected.
* `auth.authorization.type` must be a single HTTP token — no spaces. The
  permitted characters are exactly:
+
----
! # $ % & ' * + - . ^ _ ` | ~   plus   0-9  A-Z  a-z
----
+
This catches the common misreading of the key as "the whole header value":
`type = Token abc123` would otherwise emit
`Authorization: Token abc123 <credentials>`. It is a safety rule, not an
allowlist; it rejects no legitimate scheme keyword.

These errors name the offending key and never echo its value, so a credential
pasted into the wrong key does not reach the Karaf log.

For a plain bearer token use `auth.bearer.token`. It produces exactly the same
header as `auth.authorization.type = Bearer` with the same credentials — the
two are alternative spellings of one thing, not composable: setting both is a
startup failure like any other pair of auth blocks.

Dynamic schemes that require request signing or token refresh (AWS SigV4,
OAuth2, GCP IAM, Azure AD) are out of scope here: they need a signer, not a
static configuration value. Challenge-response schemes that need a round trip
with the server before the credential can be computed fall on the same side of
that line. The block sends a static, precomputed credential on every request —
if that is what your backend accepts, it fits.

[#keeping-secrets-out-of-the-cfg]
== Keeping secrets out of the configuration file

You do not have to write secrets into `{cfg-file}`. Karaf resolves two
placeholder forms in configuration values before the plugin ever sees them,
and both are available with no container reconfiguration. Verified on OpenNMS
Horizon 36.0.3 (Karaf 4.4.x).

The two forms are different mechanisms, which is why their syntax differs.
`${env:NAME}` is substituted when Karaf reads the `.cfg` file, before any key
means anything to the plugin. `$[secret:name]` is resolved by a Config Admin
plugin when the configuration is delivered. Both cover the keys in this file;
only the first is guaranteed to cover every key of every bundle.

=== Environment variables: `${env:NAME}`

[source,properties]
----
auth.bearer.token                    = ${env:PROM_TOKEN}
http.headers.cf-access-client-secret = ${env:CF_SECRET}
write.url                            = http://${env:BACKEND_HOST}:9090/api/v1/write
----

Resolution happens when Karaf reads the `.cfg`, before any key means anything
to the plugin, so it applies to *every* configuration key and works anywhere
in a value, not just as the whole value.

=== Secret files: `$[secret:name]`

[source,properties]
----
auth.bearer.token = $[secret:prom-token]
----

This reads the file `prom-token` from the directory Karaf points
`secretsdir` at, which ships pre-set to `etc/`, and uses its content as the
value. Reach for this form when your secrets arrive as files, which is the
shape a Kubernetes `Secret` volume mount, the Secrets Store CSI driver and
HashiCorp Vault Agent all produce. It keeps the secret behind filesystem
permissions rather than in the process environment.

NOTE: The file must land in the directory `secretsdir` names. Mounting a
Kubernetes `Secret` there has not been verified by this project, and note the
upstream caveat that a `subPath` mount — the usual way to place a single file
at a fixed path — does not receive Secret updates. Neither placeholder form
re-reads its source while the plugin runs: `${env:NAME}` is fixed for the life
of the process, and a changed secret file is picked up on the next
configuration reload, not immediately.

CAUTION: The file's content is used as-is, including a trailing newline. For
`http.headers.*` values that newline is rejected at activation by the CR/LF
guard; other keys strip surrounding whitespace, so it is dropped harmlessly.
Writing the file without one is the safe habit either way
(`printf '%s' "$TOKEN" > prom-token`). A missing or empty secret file yields
an empty value, which then behaves per the table below.

=== When a reference does not resolve

Karaf resolves an unset `${env:NAME}` to an *empty string*. It does not pass
the literal through, so a misspelled variable never reaches the backend as a
nonsense credential. What happens next depends on the key, and the difference
matters:

[cols="2,3",options="header"]
|===
| Key | Behaviour when the resolved value is empty

| `write.url`, `read.url`
| The plugin refuses to start, naming the key.

| `http.headers.*`
| The plugin refuses to serve, naming the header. The diagnostic says "empty
  value" — if you see that on a header you believe you set, check the variable
  name first.

| `auth.basic.username` / `auth.basic.password`
| If one of the pair is set and the other resolves empty, the plugin refuses
  to start. If *both* resolve empty, Basic auth is simply off.

| `auth.bearer.token`, `tenant.org-id`
| **Silent.** An empty value is indistinguishable from "not configured", so
  the plugin starts and sends no credential.

| `auth.authorization.type` / `auth.authorization.credentials`
| The plugin refuses to start, naming whichever half resolved empty, as long
  as the other half is set. This is why `type` has no default: a defaulted
  `Bearer` would make an empty type silent, and send the wrong scheme. If
  *both* halves resolve empty the block reads as "not configured" and the
  plugin starts with no credential — so keep at least one of the two a
  literal, which the recommended shape (literal `type`, `${env:}`
  `credentials`) does for you.
|===

WARNING: For `auth.bearer.token` and `tenant.org-id` the plugin cannot detect
a typo'd variable name. Karaf resolves the reference to an empty value before
the plugin sees the configuration, and blank already means "disabled" for
these keys, so the two cases are identical by the time any validation could
run. The plugin logs its effective authentication at startup
(`prometheus-remote-writer authentication: ...`); check that line reads what
you expect after changing an `${env:}` reference.

[NOTE]
====
**A value written literally is cleartext on disk.** If you do not use either
placeholder form above, restrict filesystem permissions on `{cfg-file}`
(owner-readable only), or render it at deploy time:

[source,shell]
----
envsubst < remote-writer.cfg.template > \
  /opt/opennms/etc/org.opennms.plugins.tss.prometheusremotewriter.cfg
----

[source,properties]
----
# remote-writer.cfg.template — $CLIENT_ID and $CLIENT_SECRET expanded at deploy time
http.headers.cf-access-client-id     = $CLIENT_ID
http.headers.cf-access-client-secret = $CLIENT_SECRET
----

Note that deploy-time templating writes the resolved secret to disk, whereas
`${env:NAME}` and `$[secret:name]` leave only a reference there.

WARNING: That distinction is lost if you edit this PID from the Karaf shell.
`config:edit` / `property-set` / `config:update` writes the *resolved*
dictionary back to `{cfg-file}`, replacing your placeholder with the expanded
secret in cleartext. `config:list` will also display the resolved value. Edit
the file directly when you are using either placeholder form.
====

== Wire format

|===
| Key                          | Default | Purpose

| `wire.protocol-version`      | `1`     | `1` = `prometheus.WriteRequest` (v1); `2` = `io.prometheus.write.v2.Request` with string interning. See <<wire-protocols>>.

== Write pipeline (in-memory)

Used when `wal.enabled=false` (the default). When the WAL is enabled,
`queue.capacity` is ignored.

[cols="2,1,4",options="header"]
|===
| Key                          | Default | Purpose

| `queue.capacity`             | `10000` | Bounded in-memory queue. Overflow throws `StorageException` — OpenNMS sees the failure.
| `batch.size`                 | `1000`  | Maximum samples per Remote Write POST.
| `flush.interval-ms`          | `1000`  | Flush whenever batch fills OR this interval elapses.
| `retry.max-attempts`         | `5`     | 5xx retry budget per batch.
| `retry.initial-backoff-ms`   | `250`   | First backoff after a 5xx.
| `retry.max-backoff-ms`       | `10000` | Backoff ceiling.
| `shutdown.grace-period-ms`   | `10000` | Bounds the graceful-shutdown wait. With WAL enabled, bounds the in-flight HTTP wait, not a drain window.
| `writer.shards`              | `1`     | Write-pipeline parallelism. N>1 splits the queue-mode pipeline into N shards (disjoint series by label-set hash, one flusher and ≤1 in-flight request each) — per-series order preserved, shards flush in parallel. Rejected with `wal.enabled=true`; capped at `http.max-connections`; requires `queue.capacity / N ≥ batch.size`. The backend sees up to N concurrent streams.
|===

== HTTP client

[cols="2,1,4",options="header"]

| Key                          | Default | Purpose

| `http.read-timeout-ms`       | `30000` | Response read timeout.
| `http.write-timeout-ms`      | `30000` | Request write timeout.
| `http.max-connections`       | `16`    | Per-route OkHttp connection pool size.

[#custom-http-headers]
== Custom HTTP headers

Operators can attach arbitrary HTTP headers to every outbound request — the
write client AND the read client both receive the same set. The use cases
this unlocks: header-based auth schemes outside Basic/Bearer (Cloudflare
Access service tokens, vendor API keys), custom tenant routing headers,
and per-instance `User-Agent` overrides for audit-log distinguishability.

[cols="3,1,4",options="header"]
|===
| Key                                  | Default | Purpose

| `http.headers.<header-name>`         | _(none)_ | Each property whose key starts with `http.headers.` is attached as an outbound HTTP header. The suffix after the prefix is the header name; the property value is the header value.
|===

Properties without the prefix are ignored. Multiple headers are configured
with multiple properties — there is no delimited-string form.

[NOTE]
====
Operator casing on header names is preserved on the request builder, but
HTTP/2 mandates lowercase header names on the wire (RFC 7540 §8.1.2), and
OkHttp negotiates HTTP/2 by default with any backend that supports it.
Operators who care about wire-side header casing (rare — most servers
match case-insensitively) must verify their backend negotiates HTTP/1.1.
====

=== Example: Cloudflare Access service tokens

[source,properties]
----
http.headers.cf-access-client-id     = 9a4f8c3a2e...
http.headers.cf-access-client-secret = 7c8eb18f...
----

Both headers are attached to every outbound request (writes AND reads). A
Cloudflare-Access-protected Mimir, VictoriaMetrics, or Grafana Cloud
endpoint will accept both directions transparently.

=== Reserved header names

The following header names are reserved. If any appears under
`http.headers.*` (case-insensitive comparison) the plugin refuses to serve
until the entry is removed:

[cols="2,3",options="header"]
|===
| Name                                 | Why reserved

| `Content-Type`                       | Set per `wire.protocol-version`.
| `Content-Encoding`                   | Must be `snappy` (protocol invariant).
| `Content-Length`                     | Recomputed by OkHttp from the body.
| `X-Prometheus-Remote-Write-Version`  | Set per `wire.protocol-version`.
| `Transfer-Encoding`, `Host`, `Connection`, `Upgrade` | Managed by the HTTP/HTTP2 layer.
| `Accept-Encoding`                    | Managed by OkHttp. Setting it disables transparent gzip, so read responses arrive compressed and fail to parse.
| `TE`, `Expect`                       | Hop-by-hop transport negotiation.
| `Www-Authenticate`                   | A response header; meaningless on a request.
| `Authorization`                      | Managed by `auth.basic.*` / `auth.bearer.token` / `auth.authorization.*`. Use those instead — `auth.authorization.type` covers non-standard scheme keywords such as `Token` and `ApiKey`.
| `Proxy-Authorization`                | The plugin does not proxy-authenticate; configure credentials on the proxy.
| `X-Scope-OrgID`                      | Managed by `tenant.org-id`. Use that instead.
|===

`User-Agent` is allowed; an operator-supplied value **overrides** the
plugin default — useful for distinguishing multiple OpenNMS instances in a
shared backend's audit log:

[source,properties]
----
http.headers.User-Agent = onms-edge-site-7/1.0
----

=== Validation

Validation runs at bean activation. Invalid configuration leaves the plugin
inert — it logs a name-only `ERROR` in the Karaf log (the offending *value*
is never echoed, for secret hygiene) and serves no requests, so a typo'd
gateway token can never degrade into requests that leave without it.

The plugin deliberately does not throw here: a throw would mark the Blueprint
container permanently failed, and a corrected file could not recover it.
Correcting `{cfg-file}` and saving is therefore intended to bring the plugin
up on the next configuration reload. That recovery path is not yet covered by
an automated test — if the plugin stays inert after a correction, restart the
bundle and please file an issue.

* Header names must match the RFC 7230 token grammar: letters, digits, and
  `!#$%&'*+-.^_\`|~` only. No whitespace; no `:`, `(`, `)`, `,`, `/`, `<`,
  `=`, `>`, `?`, `@`, `[`, `\`, `]`, `{`, `}`.
* Header values must be non-empty after trimming leading and trailing
  whitespace.
* Header values must not contain CR or LF (CRLF-injection guard).
* Header values must be printable ASCII (`0x20`–`0x7E`) plus horizontal
  tab. Operators with binary tokens should base64-encode at the source.

=== Karaf shell editing

[source]
----
karaf@root> config:edit org.opennms.plugins.tss.prometheusremotewriter
karaf@root> property-set http.headers.cf-access-client-id 9a4f...
karaf@root> property-set http.headers.cf-access-client-secret 7c8e...
karaf@root> config:update
----

Configuration reloads atomically on save; the next outbound request
carries the new header set. No bundle restart required.

=== Startup confirmation

When `http.headers.*` is non-empty, the plugin emits an `INFO` log line
listing the detected header names (values redacted) so operators can
verify intent without round-tripping through the backend:

[source]
----
INFO HttpHeadersConfig - Custom HTTP headers attached: cf-access-client-id (value redacted), cf-access-client-secret (value redacted)
----

A property-name typo (e.g., `http.header.foo` missing the `s`) shows up
here as a missing entry; check the log immediately after activation.

=== What is explicitly out of scope

* **Plugin-side environment-variable interpolation** — unnecessary: Karaf
  already resolves `${env:NAME}` and `$[secret:name]` in every configuration
  value. See <<keeping-secrets-out-of-the-cfg>>.
* **Dynamic auth providers** (AWS SigV4, GCP Identity Tokens, OAuth
  refresh) — request signing and token refresh require behavior beyond
  static header attachment; a future enhancement.
* **Multi-value headers** (same name, repeated, e.g. Accept-style). One
  value per header name.
* **Split write/read header sets** — single key drives both clients. Real
  Zero-Trust deployments (Cloudflare Access, GCP IAP) gate both
  endpoints with the same credentials, so this is the right shape today.

== Read path

[cols="2,1,4",options="header"]
|===
| Key                          | Default | Purpose

| `max-series-lookback-seconds`| `7776000` (90 d) | `findMetrics` lookback when no time window is supplied.
| `read.discovery-strategy`    | `single-pass` | Resource-discovery flow for `findMetrics`. `single-pass` issues one `GET /api/v1/series` per call. `label-values-first` opts into a two-phase path that enumerates `resourceId` values via `/api/v1/label/resourceId/values` first, then issues batched series queries with exact-match alternation. See <<resource-discovery>>.
| `read.discovery-batch-size`  | `50`    | Maximum `resourceId` values exact-match-alternated into one phase-2 selector when `read.discovery-strategy = label-values-first`. Bounds `[1, 200]`. [#resource-discovery]
=== Resource discovery (`findMetrics`)

OpenNMS discovers child resources for graph rendering, asset reports, and
search via `findMetrics(tagMatchers)`. The plugin offers two strategies for
that flow.

==== Single-pass (default)

One `GET /api/v1/series?match[]=…&start=…` call per `findMetrics` invocation.
Fast against vanilla Prometheus; the matcher-derived selector goes straight
to the backend, which evaluates it against its label index.

==== Label-values-first (opt-in)

Two-phase: Phase 1 calls `GET /api/v1/label/resourceId/values?match[]=…&start=…`
to enumerate `resourceId` values consistent with the *non-resourceId*
constraints (the `match[]` is the original matcher collection minus the
regex on `resourceId`). Phase 2 issues batched `GET /api/v1/series` calls,
each with an anchored exact-match alternation `resourceId=~"^(v1|v2|…|vN)$"`
over up to `read.discovery-batch-size` resourceIds.

The two-phase path activates only when the matcher collection contains
an `EQUALS_REGEX` matcher on `resourceId` AND no `NOT_EQUALS_REGEX` on
the same key. `NOT_EQUALS_REGEX` matchers (alone or paired with an
`EQUALS_REGEX` on `resourceId`) deliberately fall through to single-pass:
the phase-2 alternation is an inclusion form, and the helper strips ALL
`resourceId`-keyed matchers — so any negative regex would be silently
dropped, inverting the operator's exclusion intent. Exact-match callers
and matchers on other labels also stay on the single-pass path even with
the toggle on.

==== When to enable

Leave the default for vanilla Prometheus. Flip to `label-values-first` for
*Mimir / Thanos / large multi-tenant backends*, where the broad regex on
`resourceId` forces the backend to scan every matching series across the
lookback window. The `label/values` endpoint is index-only on those systems
and avoids the scan; the phase-2 alternation hits label-postings rather than
the block store.

Observe the `find_metrics_two_phase_total` and `find_metrics_single_pass_total`
counters to confirm the path mix; tune `read.discovery-batch-size` against
your workload via `find_metrics_phase2_batches_total` (its quotient with
`find_metrics_two_phase_total` is the average batches per call).

NOTE: The plugin does not silently fall back from two-phase to single-pass
on phase-1 failure — a non-2xx phase-1 response surfaces as `StorageException`
identical to single-pass error semantics. Enable the toggle only when you
trust the backend's `/api/v1/label/<name>/values` endpoint to answer
correctly under your `match[]` shape.

== Label policy

[cols="2,1,4",options="header"]
|===
| Key                          | Default | Purpose

| `labels.profile`             | `native` | Baseline label schema. `native` emits the curated, bounded default set (≤ ~15 label names regardless of deployment size). `legacy` (not yet available — validation rejects it until the empirical fixture pinning the schema ships) emits the wire schema of the AGPL `opennms-prometheus-remotewrite-plugin` for drop-in migration. All other `labels.*` knobs layer on top.
| `labels.attr-mode`           | `off` | Resource string-attribute round-trip. `off` emits no `onms_attr_*`/`onms_extattr_*` labels (per-resource attribute keys otherwise create one label name each — a label-name explosion at scale). `external` emits `onms_extattr_*` for allowlisted keys only. `both` restores the unfiltered v0.4 emission. Rejected in combination with `labels.profile = legacy`.
| `labels.attr-include`        | _(empty)_ | Attribute-key globs for `labels.attr-mode = external`, matched against the raw key (e.g. `name, datname, spcname`). Only valid with `external` mode; with an empty list, `external` emits nothing.
| `labels.include`             | _(empty)_ | Glob list of source-tag keys to surface as labels in addition to the default allowlist. Snake-cased on the wire. See <<label-mapping>>.
| `labels.exclude`             | _(empty)_ | Default labels to drop. Comma-separated label names.
| `labels.rename`              | _(empty)_ | Rename a label. Comma-separated `from -> to` pairs.
| `labels.copy`                | _(empty)_ | Add a second name for a label. Comma-separated `from -> to` pairs.
| `metric.prefix`              | _(empty)_ | Prefix added to every metric name on the wire (sanitized).
|===

NOTE: Pipeline order is `defaults → exclude → include → copy → rename →
metadata`. See <<label-mapping>> for the full mental model and worked
recipes.

== Metadata passthrough

OpenNMS metadata is opt-in only. The built-in denylist always applies.

[cols="2,1,4",options="header"]
|===
| Key                          | Default | Purpose

| `metadata.enabled`           | `false` | Master switch.
| `metadata.include`           | _(empty)_ | Glob list of `<context>:<key>` patterns to surface.
| `metadata.exclude`           | _(empty)_ | Glob list to subtract from `metadata.include`.
| `metadata.label-prefix`      | `onms_meta_` | Prefix applied to emitted metadata labels.
| `metadata.case`              | `preserve` | `preserve` / `lower` / `upper`.
|===

WARNING: Metadata is an open KV store; operators put credentials in there
(`requisition:snmp-community`, `jdbc:password`, API tokens). The built-in
denylist (`*password*`, `*secret*`, `*token*`, `*key*`, `snmp-community`)
is always applied — even when `metadata.include` would match a denied key.
Leave metadata disabled unless you have an explicit use case.

== Worked example — fully configured

[source,properties]
----
# Endpoint

read.url                      = https://mimir.example.com/prometheus

# Source identity
instance.id                   = opennms-us-east
# job.name unset — job is derived per-sample from resourceId shape

# Authentication
auth.bearer.token             = ${env:MIMIR_TOKEN}

# Wire format

# Write pipeline (in-memory, used because wal.enabled=false)

batch.size                    = 2000

# HTTP

# Label policy
