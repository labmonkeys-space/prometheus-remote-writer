[#e2e-sandbox]
= End-to-end sandbox

A self-contained Docker Compose stack for manually exercising
{project-name} against real Prometheus-compatible backends. Lives under
`e2e/` in the repo and ships with a per-backend smoke harness wired into
the project Makefile.

Use it to:

- Try the plugin against a fresh Prometheus / Mimir / VictoriaMetrics
  before committing to a production install.
- Iterate on plugin code locally with a real OpenNMS Horizon container
  in the loop.
- Reproduce a backend-specific issue someone reported, with a known-good
  reference stack.

[NOTE]
====
The backend stacks are **single-core** by design: no Minion,
no ActiveMQ/Kafka, no TLS.
Sentinel exists only as a non-functional proof of concept under `e2e/sentinel`.
====

== Layout

```
e2e/
├── compose.base.yml               # shared: postgres + core + grafana + snmpd
├── compose.prometheus.yml         # extends base, adds prometheus + per-backend mounts
├── compose.mimir.yml              # extends base, adds mimir + per-backend mounts
├── compose.victoriametrics.yml    # extends base, adds vm + per-backend mounts
├── compose.headers.yml            # the prometheus stack behind an nginx auth gate
├── authgate/
│   └── nginx.conf                 # the gate: 403 without all three headers
├── opennms/
│   ├── opennms.properties.d/
│   │   ├── timeseries.properties  # activates TSS integration strategy
│   │   └── metatags.properties    # the node, interface and category metatags
│   ├── requisitions/
│   │   └── e2e.xml                # the fleet: the snmpd node with two categories
│   ├── prometheus.cfg             # plugin cfg for the prometheus backend
│   ├── mimir.cfg                  # plugin cfg for the mimir backend
│   ├── victoriametrics.cfg        # plugin cfg for the vm backend
│   └── headers.cfg                # plugin cfg for the headers stack (auth + custom headers)
├── grafana/
│   ├── datasources/               # one file per backend; the matching
│   │   ├── prometheus.yml         # compose.<backend>.yml mounts it to
│   │   ├── mimir.yml              # Grafana's provisioning dir
│   │   └── victoriametrics.yml
│   └── dashboards/                # backend-independent, mounted by compose.base.yml
│       ├── provider.yml
│       └── resource-metadata.json # the resource metadata join, exercised by the smoke
├── prometheus/
│   └── prometheus.yml             # minimal Prom config with remote-write receiver
├── mimir/
│   └── mimir.yaml                 # single-binary Mimir config
├── snmpd/                         # a net-snmp agent: the fleet's one SNMP node
├── sentinel/                      # Sentinel proof of concept, not functional end-to-end
└── tools/
    ├── smoke-metadata.sh          # the metadata gates of `make smoke`
    └── verify-*                   # CI checks: compat range, docs attributes, the badge, the smoke backend versions
```

Two nodes produce data: OpenNMS monitors itself (`selfmonitor:1`, JMX and PostgreSQL resources), and the `snmpd` container is provisioned by the smoke, or by you, as `e2e:snmpd-1` with the categories `Routers` and `Production`, so there are real interfaces with `ifDescr`, an `ifHighSpeed` and categories on the wire (no `ifAlias`: released net-snmp does not report a Linux interface alias, so that row is absent, as the docs say about an empty value).
To provision it by hand:

[source,bash]
----
ip=$(docker compose -f compose.prometheus.yml exec -T core getent hosts snmpd | awk '{print $1}')
sed "s/@SNMPD_IP@/$ip/" opennms/requisitions/e2e.xml \
  | curl -u admin:admin -H 'Content-Type: application/xml' -X POST --data-binary @- http://localhost:8980/opennms/rest/requisitions
curl -u admin:admin -X PUT http://localhost:8980/opennms/rest/requisitions/e2e/import
----

== Prerequisites

- Docker 24+ with Compose v2.
- Build the KAR first so the `core` container can pick it up from the
  mounted `assembly/kar/target`:
+
[source,bash]
----
make kar
----

== Running

One compose file per backend — nothing else to match up. The base
services (postgres, core, grafana, snmpd) are defined once in
`compose.base.yml`; each backend file `extends:` them and appends the
backend-specific plugin cfg and Grafana datasource mounts.

[source,bash]
----
# Prometheus
docker compose -f e2e/compose.prometheus.yml      up -d

# Grafana Mimir
docker compose -f e2e/compose.mimir.yml           up -d

# VictoriaMetrics
docker compose -f e2e/compose.victoriametrics.yml up -d
----

First boot of the `core` container can take several minutes while
OpenNMS creates the database and loads features. Watch for:

```
Starting Karaf...
```

Grafana auto-provisions a datasource pointing at whichever backend is
active (selected by the compose file you brought up). Open
**Explore → OpenNMS (<backend>)** to run PromQL against the data
OpenNMS just wrote, or the provisioned **OpenNMS / OpenNMS resource
metadata** dashboard.
Its panels are the stats Resources with metadata, Attribute rows, Distinct attribute keys and Interface speed, a timeseries legended by the `group_left` join on `onms_resource_info`, and the Attributes and Categories tables of one resource (see <<resource-metadata>>).

== Smoke test (automated)

The smoke harness lives entirely in the project Makefile. Per project
convention, CI invokes `make smoke` directly.

[source,bash]
----
make smoke                          # default backends: prometheus, mimir, victoriametrics, headers
make smoke BACKENDS=prometheus      # single backend
make smoke BACKENDS="mimir victoriametrics"
make smoke-prometheus               # convenience wrapper, equivalent to BACKENDS=prometheus
make smoke SMOKE_TIMEOUT=300        # tighter deadline (default 600s for the first samples, and again for the fleet)
make smoke SMOKE_POLL=5             # tighter poll interval (default 15s)
----

Each backend is brought up, polled for `> 0` ingested series, and torn
down. The target depends on `kar`, so a fresh KAR is built first.
Pass/fail summary is printed at the end; on a timeout, the last 40
lines of the relevant container's `karaf.log` are dumped before
teardown.

Between the first samples and the teardown the harness gates on:

* the fleet (`e2e/tools/smoke-metadata.sh`): the `e2e` requisition is imported over REST and the snmpd node's interfaces collected; then `onms_resource_attr` carries `ifDescr=eth0` and an `ifName` row (a label too, but the flow reports read the row), no row repeats a data-series label or a category (`nodeLabel`, `foreignSource`, `foreignId`, `location`, `cat_*` must match nothing), `onms_resource_category` carries `Routers` and `Production`, `onms_resource_info` carries `if_descr=eth0` and `onms_resource_ifspeed` equals the agent's live `ifHighSpeed × 1e6`, read from the snmpd container with `snmpget`; the documented `group_left` join, the utilisation divisor and the category membership join each return a series; over an info series duplicated in the query with `label_replace`, the fixture holds two series per `resourceId` and the documented join still returns a series (#241); and the `@ end()` idiom and its pinned join evaluate on the backend;
* the distinct label-name count, metadata rows included, staying at or under `SMOKE_LABEL_BOUND` (the property of issue #112);
* the provisioned dashboard: Grafana reports it, and its join panel's query returns frames through Grafana's `/api/ds/query`;
* `/api/v1/label/resourceId/values` enumerating resources, and the `opennms:prometheus-writer-stats` Karaf command rendering its table.

== Verifying the plugin is active

[source,bash]
----
# Karaf shell (default admin/admin)
ssh -p 8101 admin@localhost
----

Inside Karaf:

```
karaf@root()> feature:list | grep prometheus-remote-writer
karaf@root()> bundle:list | grep prometheus-remote-writer
karaf@root()> opennms:prometheus-writer-stats
```

For what `opennms:prometheus-writer-stats` reports, see
<<operations,Operations>>.

== Querying the backend

Once OpenNMS has collected a few samples (default interval: 5 minutes
on a fresh provisioning), query the backend directly.

**Prometheus:**

[source,bash]
----
curl 'http://localhost:9090/api/v1/series?match%5B%5D={__name__=~".%2B"}' | jq .
# no scrape targets in the sandbox, so there is no `up` series; count what the plugin wrote instead
curl 'http://localhost:9090/api/v1/query?query=count({__name__=~".%2B"})' | jq .
----

**Mimir** (requires the `X-Scope-OrgID` header; tenant is `e2e` per the cfg):

[source,bash]
----
curl -H 'X-Scope-OrgID: e2e' \
  'http://localhost:9009/prometheus/api/v1/series?match%5B%5D={__name__=~".%2B"}' | jq .
----

**VictoriaMetrics:**

[source,bash]
----
curl 'http://localhost:8428/api/v1/series?match%5B%5D={__name__=~".%2B"}' | jq .
----

== Tear down

Use the same `-f` you brought the stack up with:

[source,bash]
----
docker compose -f e2e/compose.prometheus.yml down -v --remove-orphans
----

`-v` removes the named data volumes (postgres, opennms, prometheus,
mimir, vm). Drop `-v` if you want to keep state across restarts.

== Iterating on the plugin

The `assembly/kar/target` directory is mounted read-only into
`/opt/opennms/deploy/`. A rebuild of the KAR (`make kar` from the repo
root) does **not** auto-reload the plugin — Karaf's hot-deploy watches
file timestamps, but the container sees the mount at a point in time.
To reload a freshly built KAR:

[source,bash]
----
# From the repo root
make kar

# Restart only the core container (use whichever compose file is active)
docker compose -f e2e/compose.prometheus.yml restart core
----

Or, inside the Karaf shell, `feature:uninstall` + `feature:install`
cycles the plugin without restarting the container.

== What's NOT exercised here

- **Minion / remote pollers** — this is a single-core sandbox.
- **ActiveMQ / Kafka messaging** — not needed for the local TSS path.
- **TLS.** All cleartext on the compose network. Auth is exercised by
  the `headers` stack: `auth.authorization.*` (`Authorization: Token …`)
  plus two `http.headers.*` entries behind an nginx gate that 403s
  without all three, still over cleartext.
- **Sentinel.** `e2e/sentinel` is a non-functional proof of concept
  (`make sentinel-poc`), not part of the smoke.
- **Multi-tenant routing** beyond Mimir's default `e2e` tenant.
- **Dashboards beyond the one example.** Build your own in **Explore**
  or by dropping JSON next to `grafana/dashboards/resource-metadata.json`.
  The provider picks it up within 30 seconds.
