[[grafana]]
= Grafana quickstart

The label schema is designed so that Grafana's standard Prometheus data source works against the backend with *no plugin configuration beyond the two URLs*.

. In Grafana, add a *Prometheus* data source pointing at your backend's query endpoint, the same base URL as the plugin's `read.url` (e.g. `http://victoriametrics:8428`, `http://mimir:9009/prometheus`, `http://prometheus:9090`).
. There is no step two.
  Every data series carries the bounded label set; the resource's attributes are one `group_left` join away, and no relabeling or recording rules are required.

Four starter queries:

[source,promql]
----
# Interface throughput for one node, legended by interface name
rate(ifHCInOctets{node_label="router1"}[5m]) * 8

# The same, legended by the interface alias an operator set on the switch
rate(ifHCInOctets{node_label="router1"}[5m]) * 8
  * on(resourceId) group_left(if_alias)
    group by (resourceId, if_alias) (
      topk by (resourceId) (1, timestamp(onms_resource_info) or max_over_time(timestamp(onms_resource_info)[30m:1m]))
    )

# Interface utilisation, the speed gauge as a plain divisor (0 = unknown, skipped)
rate(ifHCInOctets[5m]) * 8
  / on(resourceId) (last_over_time(onms_resource_ifspeed[30m]) > 0)

# Which nodes ship the most series? (capacity view)
count by (node_label) ({__name__=~".+"})
----

`node_label`, `location` and `if_name` appear when the matching core metatags are configured (see <<configuration>>).
`job` is always present; `node`, `instance`, `resource_type` and `resource_instance` are present when the `resourceId` parses or the node identity is known (see <<label-mapping>>).
The metadata series are emitted every 15 minutes, so the right-hand side of a join always looks back twice that, and keeps the newest series per resource so a renamed alias cannot fail the join.
The full label set is described in <<label-mapping>>; the metadata series, the join idioms and why they keep the newest series are in <<resource-metadata>>.
